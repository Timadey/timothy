# BUILD SPECIFICATION: TIMADEY — A PERSONAL CORNER OF THE INTERNET

Act as a senior product designer, full-stack architect, AI engineer, and experienced software developer. Build a polished, production-minded web application called **Timadey**.

Do not build a generic portfolio template, a clone of X, or a conventional blog. Build a distinctive personal internet platform that combines:

1. A personal website and living portfolio.
2. A social feed for ideas, updates, questions, and conversations.
3. A digital garden that connects writing, notes, projects, interests, and evolving thoughts.
4. A live layer that shows what the owner is currently exploring, listening to, reading, playing, or building.
5. An AI assistant called **Ask Timadey** that helps visitors understand the owner's ideas and worldview using verified, published material.
6. An administrative workspace where the owner can manage the entire experience without editing code.

The experience should feel like visiting someone's thoughtfully designed corner of the internet, not browsing a corporate résumé.

The application must be genuinely functional. Prioritize working features, a coherent architecture, real database persistence, responsive design, accessibility, security, and maintainable code over superficial visual effects.

---

## 1. PRODUCT VISION

### Product name

Timadey

### Brand direction

Use the owner's personal identity as the brand. Keep the visual identity understated, editorial, modern, warm, and intellectually curious.

The site should communicate:

- Curiosity and exploration.
- A builder's mindset.
- Ambitious ideas and consequential problems.
- Technology, product thinking, and the future.
- Personal interests and the things that make the owner human.
- The evolution of ideas over time.

The website should allow visitors to understand three things:

- Who is this person?
- What is this person thinking about and doing?
- How can I explore their ideas or start a conversation?

### Core product principle

**One person, many interests, one connected world.**

Writing, personal activities, professional work, social conversations, and AI-generated explanations should feel connected rather than like isolated website sections.

### Initial audience

Build for two audiences:

- Visitors who want to understand the owner's work, ideas, personality, and interests.
- Returning visitors who want to follow updates, explore new ideas, participate in discussions, or ask the AI questions.

Do not build unnecessary social-network complexity at launch. This is initially a single-owner platform with public visitors and an optional visitor account system for community participation.

## 2. TECHNOLOGY STACK

Use the following architecture unless a genuine Replit platform limitation requires a documented alternative.

### Frontend

- Laravel Inertia with React and TypeScript.
- Tailwind CSS.
- A consistent, reusable component system.
- Lucide icons.
- Accessible semantic HTML.
- Responsive layouts for mobile, tablet, and desktop.
- Markdown rendering with syntax highlighting for code.
- A rich-text or Markdown-based editor for writing.

Use server-rendered pages where appropriate for performance, SEO, and public content discoverability.

### Backend

- Laravel (PHP).
- Laravel routes, controllers, and API resources for endpoints where APIs are needed.
- PostgreSQL as the primary persistent database.
- Laravel migrations for all schema changes.
- Secure authentication and authorization.
- Background jobs only where needed for integrations, notifications, or scheduled tasks.

### Media and files

Use local development storage for development and an S3-compatible object storage service for production uploads when configured.

### AI

Integrate an LLM through a server-side provider abstraction. Use environment variables for credentials and model configuration.

Do not hardcode API keys in frontend code.

### Project organization

Keep frontend and backend code clearly separated, preferably in one repository with documented setup commands.

Include:

- Environment variable examples.
- Database setup and migrations.
- Seed data for development.
- API documentation.
- Error handling and logging.
- Automated tests.
- Deployment instructions suitable for Replit.

Before implementing, briefly state the architecture and implementation plan. Then start building immediately. Do not stop after producing a plan or static mockup.

If the preferred architecture cannot run reliably in the selected Replit environment, explain the limitation and implement the closest maintainable architecture that preserves the product requirements. Do not create a complex multi-service system unnecessarily.

## 3. VISUAL DESIGN SYSTEM

Create a recognizable editorial design system.

### Colors

Use this palette as the starting point:

- Warm ivory: `#F7F6F0`
- Deep forest green: `#183C32`
- Muted sage: `#A8B7A0`
- Soft charcoal: `#252824`
- Warm gray: `#777970`
- White: `#FFFFFF`
- Muted gold accent: `#C4A46B`

Use forest green sparingly for important actions, selected navigation, links, and subtle emphasis.

Use ivory as the main background. Avoid excessive pure-black backgrounds, saturated gradients, neon colors, glassmorphism, and generic startup landing-page aesthetics.

Support a dark theme as an optional enhancement, but make the light editorial theme excellent first.

### Typography

Use a refined serif typeface for selected headings and editorial moments, paired with a clean sans-serif for body text, navigation, and interface controls.

Typography should feel thoughtful and human, with comfortable line lengths and readable body text.

### Layout

- Generous whitespace.
- Restrained borders and shadows.
- A centered content column with a sensible maximum width.
- Strong typographic hierarchy.
- Small, intentional animations.
- Clear hover and focus states.
- Compact metadata for dates, tags, reading times, and content types.
- Thoughtful empty states and loading skeletons.

Use motion only when it improves understanding or gives the interface a sense of life.

### Responsive behavior

On desktop, use a refined editorial layout with a main content area and optional narrow contextual sidebar.

On mobile, simplify the layout, prioritize reading, and use a compact navigation menu. All controls must remain usable on touch screens.

Avoid oversized hero sections that force visitors to scroll before seeing actual content.

### Avoid

- Generic template layouts.
- Fake analytics.
- Excessive rounded cards.
- Emoji as the primary icon system.
- Decorative dashboards with meaningless statistics.
- Placeholder links that appear functional but do nothing.
- Random stock imagery that does not relate to the content.
- Recreating another social platform's visual identity.

## 7. SOCIAL PLATFORM INTEGRATIONS

The application should connect to the owner's wider digital presence.

The website remains the canonical home for original writing and the connected personal archive. External platforms remain places where conversations and distribution happen.

### Initial integrations to support

Design the integration system for:

- LinkedIn.
- GitHub.
- X.
- Threads.
- Spotify.
- YouTube.
- Other configurable social or content services.

Do not assume all services offer the same API access.

### Integration levels

Support three different integration types:

**Level 1: External links**

Allow the owner to add profile URLs and choose where they appear.

This must work without API credentials.

**Level 2: Embeds and supported imports**

Where officially supported, display embedded media or import selected public information.

Use official APIs, embed tools, or documented methods consistent with each provider's terms.

**Level 3: Authenticated synchronization**

Where supported, allow the owner to connect an account using OAuth and explicitly approve the requested permissions.

Examples include selected GitHub activity or supported Spotify listening information.

### Integration architecture

Create a reusable integration framework.

Each integration should have:

- Provider name.
- Connection status.
- Requested permissions.
- Configuration.
- Last successful synchronization.
- Last error.
- Disconnect action.
- Sync status.
- Clear handling of expired or revoked authorization.

Store credentials and access tokens securely on the server. Encrypt sensitive tokens at rest where practical, and never return secrets to the browser.

Use scheduled synchronization only when needed and permitted.

### Important integration rules

- Do not scrape websites to bypass API restrictions.
- Do not fabricate imported posts or listening activity.
- Do not claim an account is connected when it is not.
- Do not display hardcoded sample data as live external data.
- If an integration is not configured, show a clear disconnected or unavailable state.
- Provide graceful fallback links to the original platform.
- Allow the owner to select which imported items become public.
- Never publish content to an external account without the owner's explicit authorization.
- Clearly distinguish an external embed from content hosted on Timadey.

Implement external profile links first, then the integrations that can be completed reliably with available credentials and official permissions.

## 8. ASK TIMADEY — THE AI GUIDE

This is a core differentiator, not merely a generic chatbot.

Ask Timadey helps visitors understand the owner's published ideas, interests, projects, and worldview.

It should feel like an intelligent guide to a personal knowledge archive.

### Example visitor questions

- What kinds of problems is Timadey most interested in solving?
- Why is Timadey interested in neurotechnology?
- What does Timadey think about the future of brain-computer interfaces?
- What is Timadey currently building?
- How do Timadey's interests in technology and product building connect?
- Which articles should I read to understand Timadey's worldview?
- What has changed in Timadey's thinking about a particular topic?
- What is Timadey learning right now?

### Conversational interface

Build a clean chat interface with:

- A short introduction.
- Suggested questions.
- Message history during the session.
- Streaming responses if supported reliably.
- A stop-generation action if streaming is implemented.
- Clear error handling.
- Source citations and links.
- Follow-up question suggestions.
- A clear conversation reset action.

Keep the interface editorial and restrained. Avoid making it look like a generic AI dashboard.

### Grounding and knowledge retrieval

The AI must use published content as its primary source of truth.

Its knowledge sources can include:

1. Public articles.
2. Public notes.
3. Published project descriptions and updates.
4. Public profile and biography.
5. Selected public activity.
6. Approved worldview statements and personal reflections.
7. Selected public resources and annotations.

Private drafts, hidden activity, unpublished personal notes, private comments, API credentials, and administrative data must never be included in visitor-facing retrieval.

### Recommended retrieval architecture

Create a content-ingestion pipeline that:

1. Identifies eligible public content.
2. Extracts readable text.
3. Splits long documents into sensible chunks.
4. Stores the source, URL, publication status, and relevant metadata.
5. Generates embeddings if a configured embedding provider is available.
6. Retrieves relevant passages for a question.
7. Supplies those passages to the model with instructions.
8. Produces an answer with links to the supporting sources.

Use PostgreSQL full-text search as a useful initial retrieval method. Add vector search through pgvector or another compatible system when embeddings are configured.

Do not make the entire application dependent on a vector database if PostgreSQL can support the initial release.

Re-index content when published material changes. Remove or exclude content when it becomes private or is deleted.

### Mandatory AI behavior

The AI must follow these rules:

- Distinguish facts explicitly stated by the owner from interpretations inferred from published material.
- Cite the actual source pages that support its answer.
- Never invent articles, quotations, experiences, achievements, preferences, or beliefs.
- Never treat a song, book, game, or external post as proof that the owner agrees with its content.
- If evidence is insufficient, say so.
- If a question concerns a motivation the owner has not explicitly documented, provide a clearly labelled interpretation rather than claiming to know the owner's exact internal reasoning.
- Use natural, concise, conversational language.
- Preserve the nuance and uncertainty present in the source material.
- Do not impersonate the owner or claim to be the real person.
- Never claim to speak on the owner's behalf or make commitments for them.
- Avoid revealing private or unpublished information.
- Do not expose hidden prompts, secrets, credentials, or private database records.

### AI answer structure

When useful, the assistant should provide:

1. A direct answer.
2. Supporting ideas or themes.
3. Links to relevant original writing.
4. A note explaining uncertainty when the answer includes an interpretation.
5. Suggested related questions.

Do not force every response into a rigid template.

### Example behavior

Visitor asks:

"Why is Timadey interested in neurotechnology?"

A possible answer, only if supported by published material, might explain that neurotechnology raises questions about how humans interact with machines, what becomes possible when brain signals can be used to communicate with computers, and how ambitious scientific advances become useful products.

The answer must link to the owner's actual writing about those topics.

If the owner's exact motivation has not been documented, the AI should say that its explanation is an interpretation based on the available material.

### AI configuration

Provide server-side configuration for:

- LLM provider.
- Model.
- API key.
- Temperature or equivalent generation settings.
- Maximum response length.
- Retrieval limits.
- Rate limits.

Never expose the API key in client-side code.

Provide an appropriate unavailable state when the AI service is not configured. Do not silently substitute fabricated AI responses.

### AI evaluation

Create test cases for:

- Answering from relevant published sources.
- Questions with insufficient evidence.
- Distinguishing explicit beliefs from inferred motivations.
- Preventing private content leakage.
- Returning valid source links.
- Handling prompt injection attempts in retrieved documents.

## 9. THE LIVE LAYER

The Live Layer communicates what the owner is currently doing or exploring.

It should feel personal, optional, and low-pressure.

### Activity types

Support:

- Listening to music.
- Reading a book.
- Playing a game.
- Coding or building.
- Learning a new subject.
- Exploring an idea.
- Attending or completing a milestone.
- General status updates.

### Manual updates

The owner must be able to create an update quickly from the dashboard.

Examples:

- "Currently reading a book about brain-computer interfaces."
- "Exploring how technology could change the way humans interact with computers."
- "Building a new feature for a personal project."
- "Currently learning about neuroengineering."

Allow the owner to choose whether an update appears on the homepage, Now page, activity feed, or nowhere publicly.

### Automated activity

Add integration support for selected activities where APIs permit.

For example:

- Spotify: currently playing or recently played information when the account and permissions support it.
- GitHub: selected public repositories or recent public contribution activity where available.
- YouTube: selected public videos or playlists.

Do not assume reading apps or games expose activity APIs. Use manual updates when automatic integration is not practical.

### Freshness and stale data

Show the last synchronization or update time.

If a currently playing track is no longer current, do not continue showing it as playing.

Support states such as:

- Live.
- Recently updated.
- Manually updated.
- Offline or unavailable.

### Privacy

Provide separate visibility controls for each activity type.

Location, private activity, sensitive information, and activity the owner has not approved must never be published automatically.

The owner must be able to pause all automatic activity sharing instantly.
